# Maintenance Loop

**Purpose:** Evaluate whether the project remains sustainable, internally consistent, and operationally healthy over time.

- **Scope:** stale artifacts, obsolete configuration, dependency health, abandoned or duplicate mechanisms, process debt, validation health, release hygiene, version and manifest consistency, installation drift, public sanitization, compatibility claims, recurring defects, warnings, and lifecycle obligations.
- **Inputs and evidence:** project inventory, histories, validation results, dependency and release data, maintenance records, and cross-artifact comparisons.
- **Owns:** findings whose proposition concerns sustainability, freshness, or operational upkeep.
- **Observes:** all project surfaces for drift and recurring cost.
- **May recommend:** retirement, consolidation, updates, automation, ownership, or explicit debt tracking.
- **May not decide:** product semantics, unrestricted aesthetic refactoring, destructive cleanup, or deletion authority.
- **Must hand off:** behavioral defects to Implementation; architectural duplication to Architecture; user impact to Adoption; unresolved lifecycle state to Disposition.
- **Finding types:** stale artifact, unsupported dependency, duplicate mechanism, recurring failure, ownership gap, manifest drift, version drift, project-specific leakage, stale compatibility claim, or release/process debt.
- **Output:** canonical findings, recurrence links, handoffs, and one loop result.
- **Termination:** selected maintenance signals and recurrence history were evaluated.
- **Rerun:** inventory, dependency, validation, release, or recurrence evidence changes.
- **Failure modes:** cleanup as an end in itself, semantic changes disguised as hygiene, or treating age alone as defect evidence.
